# exp03_event_rolling

**status:** planned（目录与 notes 已建；`run.py` / `config.yaml` 待实现）

**论文锚点:** §3.5.6 动态滚动场景下的适应性分析  
**不负责:** 算法性能排名、选择层规模扫、完整基线竞赛（见 exp02 / exp05）

---

## 目的

在 **多周期滚动** 框架下，验证方法对 **动态事件** 的响应是否符合问题定义，而不是只跑“平滑到达、无故障”的理想轨迹。

具体回答：

1. 任务池是否按 \(\mathcal{T}_t = \mathrm{remain}\cup\mathrm{new}\cup\mathrm{release}\) 演化，且 \(\mathcal{T}_t^{\mathrm{exec}}\subseteq\mathcal{T}_t^{\mathrm{sel}}\subseteq\mathcal{T}_t\) 始终成立？
2. 注入 UAV 故障 / 突发高优先级任务 / 机巢不可用后，是否触发重规划或强制纳入，且释放任务不丢失？
3. 滚动过程中完成率、滞留年龄、按时率、硬违约是否保持可解释的变化（而非偶然单次成功）？

## 建议场景与因素设计

### 基线场景（无事件对照）

- 地理 / 机巢 / DEM：与 exp01 同一数据源（便于口径一致）
- 规模建议：任务流持续到达，使多周期池非空；机队 \(K\) 与任务量避免“全程空转”
- 周期数：建议 ≥5（过短看不出滞留与释放）
- seeds：正式结果 ≥5；调试可单 seed

### 事件因子（建议一次一类，再做一个组合压力）

| 因子 ID | 事件 | 注入方式（配置级） | 期望行为 |
|---------|------|-------------------|----------|
| E0 | 无事件 | 关闭全部 fault/burst/nest_close | 对照轨迹 |
| E1 | UAV 故障 | 指定周期、指定机 ID 故障；未完成任务 → release | 任务回池；可用机下降；可强制重规划 |
| E2 | 突发高优先任务 | 某周期插入高 reward / 紧 latest 任务 | forced 纳入或优先级顶入 sel |
| E3 | 机巢不可用 | 某巢 `available=false` 或容量骤降 | 终点候选剔除；不落不可用巢 |
| E4 | E1+E2 或 E1+E3 | 组合 | 压力；只作补充，不作唯一证据 |

成功不要求“越多事件指标越好”，要求 **行为符合协议** 且指标可解释。

## 成功标准

1. **结构:** 全种子、全周期 `exec ⊆ sel ⊆ pool`；release 任务出现在后续 \(\mathcal{T}_t\)；无静默丢任务。
2. **事件响应:** E1/E2/E3 各自至少一次被检测并写入 `run_meta` / metrics 事件日志；对应配置下行为与上表一致。
3. **对照:** E0 与 E1（或 E3）在同学种子上可对比：可用机数、完成量、滞留分布、重规划次数有差异且方向合理。
4. **可行:** 硬违约不因事件注入而系统性爆炸；若升高，需在 notes 记录原因（资源变紧属预期）。
5. **可复现:** `config.yaml` 固定事件时刻表与 seed；`results/` 含 `metrics.json`、`run_meta.json`、事件摘要。

## 主指标（与全局口径一致）

| 类 | 指标 |
|----|------|
| 效果 | 有效完成率、奖励产出率、周期完成量 |
| 时间 | 按时率、总迟到、平均/最大等待（滞留年龄） |
| 动态 | 每周期 \(\|\mathrm{remain}\|,\|\mathrm{new}\|,\|\mathrm{release}\|\)；重规划次数 |
| 可行 | 硬违约次数、执行弹回次数 |
| 事件 | 故障机次数、强制纳入任务数、不可用巢导致的终点变更次数 |
