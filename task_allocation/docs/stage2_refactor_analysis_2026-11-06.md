# 第二阶段方法改进分析：修复/优化职责分离与统一决策轨迹

> 2026-11-06。依据：`methods/muas` 全量代码 + Lagaros et al. (2023)
> *Constraint handling techniques for metaheuristics: a state-of-the-art review
> and new variants*（下称 Lagaros2023），并核对仓库内已有诊断/消融结论。
> ⚠️ **2026-11-06 晚已用全文（Zotero `storage/UEDCMGSJ`）逐条复核**：§2 的 5 条
> 引用中有 4 条需校正（Baldwin/Lamarck 术语、ε 章节号、三元比较形式、「同一时刻
> 只有一个生效」），1 条无原文依据（局部搜索预算纪律）。**以
> `stage2_final_scheme_2026-11-06.md` §7 勘误表为准**，本文保留为分析底稿。
> 本文回答两个被明确指出的问题：
> 1. 修复与主动优化职责混合、缺乏统一决策轨迹与模块级归因；
> 2. 主动优化全部塞进解码链，DE 收益被稀释，精英长期不更新、polish 成主力。

---

## 0. 一句话结论

当前第二阶段把**修复（Lagaros 第 4 类 CHT）与目标驱动的邻域/混合搜索这两件事**
合并进了同一条每代、每体都执行的 `build_solution` 解码链，且只保留终态、不记录
算子来源。⚠️ 订正：Lagaros 并未把「目标驱动局部搜索」立为独立一类（全文六类为
penalty / separation / combination / repair / boundary / other，「local search」只在
§2.6 出现 3 次且用于定位可行域），所以「二者本应分立」是**我们的设计选择**，
不是原文规定；可援引的是 §2.4 的「修复可选 + 回写比例由开发者决定」与 §2.3 的
组合式 CHT 实践。目标改进不是再加开关，而是做一次
**「可行性修复 / 统一比较选择 / 显式预算的目标搜索」三层分离**，并用一条
**统一决策台账（decision ledger）** 贯穿，所有接受/拒绝走同一个比较算子、
可逐体逐算子归因。全程以开关 + A/B 分阶段落地，不做一次性重写。

## 1. 现状：优化实际发生在四个地方，且边界不清

| # | 位置 | 载体 | 性质 |
|---|------|------|------|
| ① | `inverse_phi` 内 `representation/repair_rules`（nearest_match/unique_filter/invalid_mutator/terminal_nest） | 连续试验向量 → 离散基因 | 编码边界的合法修复（合理） |
| ② | `build_solution`（`decode_repair.py`），在 `evaluate` 内**每代每体**执行，交付时再跑一次 | 表型修复链 | **可行性与目标优化混合** |
| ③ | M1 环内 memetic（`gen_callback`，每 K 代精英 polish + 档案） | 表型邻域 | 目标搜索 |
| ④ | 交付后三层 polish：`polish_assignment`、`post_polish`(coverage_first)、`post_cost_polish`(2-opt/Or-opt/relocate) | 表型邻域 | 目标搜索 |

### 1.1 问题一的机制定位：修复与主动优化在哪里被混在一起

`build_solution` 的六道不动点循环里，同时存在两类语义相反的算子：

- **纯可行性算子**（把不可行向可行移动，保 I3/I4）：`_repair_range`、
  `_repair_sequence`、`_choose_end_nests`(MCF)、`_reflow_task`、覆盖门禁。
- **目标驱动算子**（接受条件是成本严格下降）：
  - **`_consolidate`**：合并的接受判据是"总代价严格下降且不超航程"
    （`decode_repair.py:546-549`）。其中"让闲置可表达"是可行性/表示问题，
    "选最便宜的合并"是**主动优化**，二者写在同一个函数、且位于每代每体的
    不动点循环内。
  - **`_best_order`**：时间窗重排本是软约束可行性（迟到数、迟到量），但候选里
    含最近邻 NN（`decode_repair.py:343-358`），并列第三裁决键是航程；零迟到
    早退后航程成为实际决定因素。

后果：DE 在 cost 指纹空间里探索出的"谁该闲置/谁该独立"的差异，在解码阶段被
确定性贪心算子立即重合并、重排序；这些目标改进**对每个基因型一视同仁地施加，
却不写回基因**（除保守的起始通道 M1），于是它能整体抬高适应度，却**不改变
个体之间的相对排序**——DE 无法沿着这些改进继续爬。

### 1.2 问题二的机制定位：为什么精英冻结、polish 成主力

核对 `ab_mechanism_3steps/SYNTHESIS.md` 与 `ab_optimization_attribution/ab_attr_report.md`：

- 表型碰撞率 0、基因型→表型压缩 0：**不是表示坍缩**，差异确实传导到了最终解；
- 但精英**冻结代占比 ≈ 0.89**、精英平均总增益仅 11.62、改进代数 ≈ 0.2：子代在
  动，却系统性劣于初始精英，硬贪婪规则（`child.fitness < population[i].fitness`
  才替换，`dmde_solver.py:225`）几乎从不采纳；
- 池化归属：进化 18% / 精修 82%，小批量体制进化 = 0%。

机制链条：解码链已确定性地给出近优解，其中的目标改进是"事实上的 Baldwin 式"
（只用于评价、不回基因）且对全体同口径施加 → 不产生可遗传的个体间差异 → DE
选择无梯度可爬、精英从第 0 代冻结；真正强的邻域搜索（2-opt/Or-opt/relocate）
只在交付后发生，且 M2-1 巡游序回写默认关、段匹配闸门过严（`_segment_matches`
要求段任务集严格相等，一次剔除即整段作废），果实回不到进化轨迹 → polish 成为
改进的实际主力。

### 1.3 为什么现在无法做模块级归因

`build_solution` 原地改 routes、6+ 轮 pass 后只留下最终 `AllocationSolution`，
"哪个算子做了哪次改动"不被记录。现有归因只有：终态 `ConstraintReport`
的分约束违背量（最终状态、非算子来源）、`writeback_stats`（仅 M2-1 闸门计数）、
以及 stage 级聚合诊断。逐体逐算子归因目前只能靠运行时 monkeypatch（多篇诊断
文档均记录了这一成本）。

## 2. Lagaros2023 能提供的依据（全文核实后的五点，含订正）

1. **修复是独立的一类 CHT（§2.4），且「修复后个体是否回写」必须显式。**
   原文 p.2264：修复后的个体「can be used solely for fitness function evaluation
   purposes or for replacing the initial individual into the next generation」，
   且「varies between either replacing the original individual …, or only a small
   percentage, or every infeasible individual」。⚠️ 订正：**全文没有 Baldwin /
   Lamarck / memetic 字样**，这两个词是我们的术语化表述，引用时须标注；
   原文支持的是「回写比例由开发者决定」，不是「修复概率」。
   当前代码把这一选择隐式化、且因算子而异——这正是要先显式化的第一件事。

2. **目标与约束分离（§2.2）+ ε-constrained 方法（§3.3，v1 误写 §3.1）。**
   ε-level 比较：阈值内按目标、阈值外按可行性；ε 由松到紧收敛到 0。
   原始调度为 Takahama & Sakai Eq. 11，**新变体用 Fan et al. (2018) Eq. 12**。
   这给出「一条比较规则 + 一个阈值调度」，替代散落在各算子里的可行性判断。
   早期放松 ε 可让「目标好但略不可行」的子代存活，**机制上**对症精英冻结，
   但本项目尚未实测，属待验证假设。

3. **新变体不是「三元向量比较」，而是乘积式适应度 / ε 比较规则（p.2269–2272）。**
   `p_violation` = 最大（或均值/中位数）违反量 ×(1 + 违反条数/总条数)（Eq. 8a–d），
   FeasRulesNEW 的 `F(x) = max(f_best_feasible, f(x)) × p_violation`（Eq. 9b），
   EconstNEW 走 Eq. 13 的四分支比较。⚠️ 订正：v1 写成「(目标, 违背条数, 违背量)
   向量化比较」不准确；正确理解是**乘积式重标定内部适应度**，且 8a 不含违反条数。
   工程上我们只用它改 `F_sel`，不改问题目标 `f`（标定与可比性原因）。

4. **组合 CHT 是常见实践（§2.3），但「同一时刻只有一个生效」只属特定方法。**
   ⚠️ 订正：该句是 **Malan (2018) landscape-aware** 的做法；同节
   Mallipeddi & Suganthan (2010) 的 ensemble 恰是**四种 CHT 并行、各管一个种群**。
   这对本项目反而**有利**：「层 1 惩罚 + 层 2 修复 + 层 3 精修并存」属组合式 CHT，
   有先例支持；真正要回答的是「被修复与未修复个体如何同台比较」（见 §3 / 定稿 §5）。

5. **「局部搜索是预算受控组件」在原文中无依据。**
   ⚠️ 全文 `local search` 仅 3 处，均为 §2.6 中 Rosso et al. (2022) 用于
   「localize the feasible region」的算子，没有预算纪律或「只对选定个体调用」的表述。
   该原则改由本项目两条方法论铁律承担（成本优化作用于交付解 / 解码期算子干扰 DE 搜索）。

## 3. 目标架构：三层分离 + 一条决策台账

```text
基因 g
  → ① 可行性修复层（纯 repair，默认 Baldwin；只向可行移动，不做目标下降）
  → ② 统一比较/选择层（ε-constrained，三元组 (目标, 违背条数, 违背量)，单算子单阈值）
  → ③ 显式预算的目标搜索层（memetic：2-opt/Or-opt/relocate/成本合并，按状态触发）
       ↔ 受控 Lamarck 回写（过闸门才写回基因，多样性护栏）
  → 交付
  全程：Decision Ledger 记录每次 (算子, 移动, Δ目标, Δ违约, 接受与否, 闸门原因)
```

### 3.1 层① 可行性修复（从解码链中剥离目标移动）

- `_consolidate` 拆分："闲置可表达"保留为表示/可行性能力（更彻底的做法是让
  "不参与本轮"成为**基因级一等选项**，Lagaros 与本库设计注释均指向此）；
  "成本最小合并"移入层③，不再每代每体执行。
- `_best_order` 仅保留软约束可行性（迟到数、迟到量）；NN 成本候选移出每代
  路径，只在交付 pass、可行性持平时才允许以航程裁决。
- 该层对可行性单调（保 I4），不做任何会改变个体间基因型相对排序的目标移动。

### 3.2 层② 统一比较与选择（候选的最高杠杆点，尚未实测）

> 2026-11-06 拍板后的定稿口径：**默认档为 Deb 三规则「可行性优先」**，
> ε / Lagaros 两类变体只作**可选开关对照**，且全部作用在内部选择标量 `F_sel`，
> 不改问题目标 `f`（详见 `stage2_final_scheme_2026-11-06.md` §6 要素 2）。

- 用一个 ε-constrained 比较算子替换散落的可行性逻辑与硬贪婪替换；接受/拒绝
  （DE 替换、邻域接受、档案择优）全部走同一算子、记录当下 ε。
- 早期 ε 放松，使携带良好目标信息的略不可行子代得以存活，避免被初始精英一票否决；
  后期 ε→0 保证交付可行。比较键采用（目标, 违背条数, 违背量）。

### 3.3 层③ 显式预算的目标搜索（memetic 与解码解耦）

- 强邻域（2-opt/Or-opt/relocate、成本合并）改为按种群状态/固定间隔、对精英加
  一部分其他个体触发的独立预算阶段，不再是每体确定性 pass。
- 以**受控 Lamarck 回写**作为目标搜索回到基因的唯一桥梁：放宽 M2-1 段匹配闸门
  （允许段级/部分回写），并落地已设计未实现的 **M2-2 跨段迁移回写**；保留
  源过滤、表型复核、范围控制与种群方差护栏。

### 3.4 决策台账（模块级归因的基础设施）

- 逐体事件流，由各算子追加：`(代, 阶段, 算子, 移动类型, 移动任务数, Δ目标,
  Δ违约, 是否接受, 闸门原因)`。生产默认关、实验开启，性能开销可控。
- 复用现有 `ConstraintReport.violation_breakdown` 与 `writeback_stats` 作为起点，
  使"修复地板 / 进化 / 精修"的三方分解可逐体复现，不再依赖 monkeypatch。

## 4. 现有算子职责重分类（按"保护哪个不变量"而非函数名）

| 算子 | 现位置 | 真实职责 | 目标去向 |
|---|---|---|---|
| nearest_match/unique_filter/invalid_mutator/terminal_nest | inverse_phi | 编码边界可行性 | 保留 + 入台账 |
| `_consolidate`（闲置表达部分） | 每代解码 | 可行性/表示 | 保留（优先升级为基因级闲置选项） |
| `_consolidate`（成本合并部分） | 每代解码 | **目标** | 移至层③ |
| `_repair_range` / `_repair_sequence` | 解码 | 硬可行性 | 保留 + 入台账 |
| `_choose_end_nests`(MCF) | 解码 | 可行性精确解 | 保留 + 入台账 |
| `_reflow_task` / `_complete_coverage` / 覆盖门禁 | 解码 | 可行性救援(I2) | 保留 + 入台账 |
| `_reorder_for_deadlines`（迟到键） | 解码 | 软约束可行性 | 保留 |
| `_best_order` 的 NN/航程裁决 | 解码 | **目标** | 移至交付/层③ |
| M1 环内 polish | gen_callback | 目标（memetic） | 保留，纳入层②③统一调度 |
| `polish_assignment` / `post_polish` | 交付后 | 目标 | 保留，统一归层③ |
| `post_cost_polish`（2-opt/Or-opt/relocate） | 交付后 | 目标 | 保留并接 M2 回写 |

## 5. 分阶段落地（守 bit-exact 与测试基线）

| 阶段 | 内容 | 行为变化 | 验证口径 |
|---|---|---|---|
| P0 可观测先行 | 决策台账（开关默认关）+ 给 `build_solution` 各算子插桩 | 无（bit-exact） | 取得基线归因，供后续比对 |
| P1 统一比较器 | ε-constrained 三元比较器（开关 A/B） | 隔离 | 主看冻结代占比下降、精英总增益上升；可行性/覆盖不退化 |
| P2 剥离目标移动 | 拆 `_consolidate`/`_best_order`，成本移动移层③ | 中等 | 修复地板（覆盖 100%、n_hard=0）不变，比较最终目标 |
| P3 回写闭环 | 放宽 M2-1 段闸门、实现 M2-2 跨段回写 + 方差护栏 | 中等 | 交付成本显著优、方差不加速坍缩（配对 t 检验） |

### 风险与纪律

- `build_solution` 是适应度的**定义本身**，历史审查明确不建议为清晰而重排它；
  故全程开关门控、分阶段 A/B，且可行性-only 解码必须先证明覆盖/可行性地板不变。
- 保住性能红线：`_best_order` 零迟到早退是性能保护，台账与额外评估不得显著抬墙钟；
  目标搜索改为独立预算后，每代每体的确定性开销应下降而非上升。
- 分类口径：以"该移动保护 I3 硬可行性还是降低目标"判定归属，不按函数名；软约束
  （迟到）修复仍属可行性，目标下降只在可行性持平时才允许。
- 每阶段合并前满足现有门槛：exp01 审计通过、全量测试绿、论文数字与留档一一对应。
