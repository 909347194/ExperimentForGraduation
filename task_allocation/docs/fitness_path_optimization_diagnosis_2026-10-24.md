# 诊断：路径优化不足是否依然存在？（2026-10-24）

> 问题：适应度靠大值 `m·F1` 优先完成更多任务，导致 DMDE 搜索对路径优化不足、
> 收敛曲线很早收敛。改 λ=1e-1 之后，这个问题是否还在？
>
> 方法：**只用已落盘产物做反解 + 代码判据定位**，不重跑实验。
> 数据：`exp01_smoke/results/`（λ=1e-2，3 seed，指纹 `b689c69716f4e121`）。
> λ=1e-1 实测见文末补记。

---

## 0. 结论先行

**依然存在，而且 λ 改不动其中最主要的那一条。**

定量：λ=1e-2 下 `|m·F1| : |λ·path| = 8040 : 1`；λ=1e-1 把比值拉到约 **804 : 1**
（改善 10 倍），但成本项仍只是完成项的千分之一量级。更关键的是——
**路径优化的最大阻塞不在权重，而在后处理层的一行早退代码，它与 λ 完全无关**：

```python
# muas_stage.py:1078-1080  polish 重排
base_key = _evaluate(list(tids))
if base_key is not None and base_key[0] == 0:
    return list(tids)        # ← 原序零迟到 → 直接返回，航程一字不动
```

`_evaluate` 返回 `(迟到数, 迟到量, 航程)`，候选比较是**元组字典序**（航程排第 3 位），
且零迟到时连比较都不做。实测：exp01 各周期 `final_late_s = 0` ⇒ **polish 全程早退，
航程从未被优化过**。

## 1. 实证一：权重比值（适应度层）

周期1 落盘快照 `fitness_weights`：`m = 276143.71`、`λ = 0.01`、`w_hard = 3.26e8`、
`w_late = 0.01`、`w_time = 0`。

先用终值验证标量公式（其余项实测全零：`n_hard=0, excess=0, late=0`）：

```
-m·F1 + λ·path = -276143.711 × 118.2068 + 0.01 × 405978.61
               = -32642073.0 + 4059.79 = -32638013.17
落盘 final_fitness        = -32638013.17      差 = 0.0000  ✔
```

| 项 | 值 | 占比 |
|---|---:|---:|
| `m·F1` | 3.2642e7 | 99.9876% |
| `λ·path` | 4.06e3 | **0.0124%** |
| 比值 | **8040 : 1** | |

放大到「单任务」尺度更直观：周期1 执行 20 个任务、`F1 = 118.21` ⇒ 平均单任务收益
`R̄ = 5.91`，于是

```
m·R̄ = 276144 × 5.91 = 1.632e6      （多完成一个任务的适应度台阶）
λ·path 全项          = 4.06e3       （把航程压到 0 也只值这么多）
台阶 / 路径全项       = 402 : 1
```

**含义**：任何"改动一个任务归属"的变异，其适应度变化几乎全部由 F1 决定——
一个任务的台阶就是整条航程价值的 402 倍。成本项只能在"F1 完全相等"的解之间做
tie-break，而离散编码下这类变异稀少 ⇒ 选择压力实质上 100% 指向 F1。

## 3. 实证三：polish 的增益花在哪（后处理层，最关键）

`polish_gain` 名义是"成本打磨"，周期1 达 **231486**（相当于搜索期 100 代总改进的 64%）。
它到底降了航程还是加了收益？用反证法：

设 `gain = m·ΔF1 + λ·Δpath`。

| 假设 | 推论 | 是否成立 |
|---|---|---|
| 增益全部来自 path | `Δpath = 231486/0.01 = 2.31e7 m = 23,149 km` | ✘ 实测总航程仅 406 km（需 5702%） |
| 增益全部来自 F1 | `ΔF1 = 231486/276144 = 0.838` 收益单位 | ✔ 等效 0.142 个任务，量级合理 |

严格反解（`path` 不变假设下）：

| 周期 | gain | F1_before | F1_after | ΔF1 | 等效任务 | 若 ΔF1=0 所需 path_before |
|---:|---:|---:|---:|---:|---:|---:|
| 1 | 231486 | 117.369 | 118.207 | 0.838 | 0.142 | 6,504,860 km ✘ |
| 2 | 864269 | 82.818 | 86.069 | 3.252 | 0.756 | 4,488,592 km ✘ |
| 3 | 510208 | 113.357 | 115.314 | 1.957 | 0.339 | 5,961,310 km ✘ |

**三个周期一致：polish 的增益全部来自"把原本超期被丢弃的任务救回"（F1 增加），
航程贡献≈0（反证需要百万公里级航程差）。**

### 为什么？看代码

polish 的重排候选是同一组 `tids` 的几种排序（按 latest / earliest / 窗口宽度 /
最近邻），**不改变执行集**；F1 会变，是因为重排改变了 ETA，使原本超期的任务变得
不超期从而被纳入——即"救任务"。而它的比较键和早退是：

```python
def _evaluate(seq) -> tuple[int, float, float] | None:
    """返回 (迟到数, 迟到量, 航程)；超剩余航程 → None（不可行）。"""

# 候选比较：元组字典序，航程排第 3 位
if best_key is None or key < best_key:      # 先比迟到数 → 迟到量 → 航程
    ...

# 早退：原序已零迟到 → 不必重排（绝大多数航次走这条路）
base_key = _evaluate(list(tids))
if base_key is not None and base_key[0] == 0:
    return list(tids)
```

唯一以航程为目标的候选是"最近邻"（注释自称"航程最短的候选，成本维度的对照"），
但它**只在原序存在迟到时才会被尝试**。exp01 各周期 `final_late_s = 0` ⇒
**早退全中，最近邻候选从未被评估**。

> 附带影响：早退是性能保护（注释称去掉后求解 72 s → 121 s）。修的时候要同时
> 保住这条性能红线。

## 4. 三层根因汇总

| 层 | 症状 | 证据 | λ 能否缓解 |
|---|---|---|---|
| L1 适应度 | `m·F1 : λ·path = 8040:1`；单任务台阶 = 路径全项的 402 倍 | §1 | ✔ 线性改善：1e-1 → 804:1、402:1 → 40:1 |

**L3 是硬阻塞**：只要交付解零迟到（`final_late_s = 0`，exp01 常态），无论 λ 取
1e-1、1e0 还是 1e1，polish 都不会动航程。λ 只能改 L1/L2，改不动 L3。

## 6. 修复建议（按性价比排序）

1. **P0 — 拆 polish 的早退判据**（治 L3，与 λ 正交，收益最直接）
   早退条件从「零迟到」改为「零迟到 **且** 航程已在候选中不劣」：
   零迟到时仍评估最近邻候选，只在 `length` 严格更短时才替换。
   成本：去掉早退会让求解从 ~72 s 抬到 ~121 s（注释实测）⇒ 需要更窄的触发条件
   （例如只在"航程占剩余预算比例高于阈值"或"末轮"时才跑最近邻），把性能红线守住。
2. **P0 — 把航程提为 polish 的比较键之一**（治 L3 的字典序）
   在迟到数、迟到量均相同（尤其同为 0）时，以航程为裁决键——现在这个分支被早退吃掉了。
3. **P1 — 成本 polish 与主搜索解耦**（治 L1）
   不动主适应度阶梯（保住"`f` 不含 F1"的门禁口径），在主搜索后加一段**只以路径为目标**
   的局部搜索（2-opt / Or-opt 组内重排 + 跨机 relocate）。记忆里 P4「成本 polish（含跨机
   relocate）」正是这条，尚未实施。
4. **P2 — 若要彻底解决 L1/L2，只能开覆盖门禁**
   `f = λ·F2 + w_time·F3`（F1 退为事后指标）。但 10-23 的 E1/E2 已证明：门禁一开，
   完成率下降 + 淘汰出现（可行域被成本压满、后续任务装不下）⇒ 必须配合
   「覆盖优先的 polish / 二阶可行性检验」一起上，不能单点开。
5. **P2 — 把 `cost_history` 的分解落盘**
   现在曲线只有标量，事后无法判断某段下降来自 F1 还是 path（本次全靠反解）。
   建议逐代记 `(F1, path, penalty)` 三元组，成本极低。

### 8.2 ⚠️ 新发现：`m` 随 λ 联动，λ 的杠杆被自动抵消

| 档 | λ | 各周期自动推导的 m |
|---|---:|---:|
| 1e-2 | 0.01 | 276144 / 265809 / 260718 / 100478 |
| 1e-1 | 0.1 | **669115 / 685259 / 299261** |

`m` 由 `_secondary_upper_bound` 自动推导为"支配性权重"，它**随 λ 一起放大**（约 2.4×），
以维持"F1 差异永远压倒成本差异"这一性质。后果：

```
λ 放大 10×，但比值只从 8040:1 改善到 1819:1（4.4×，不是 10×）
```

**这就是"λ 是弱杠杆"的机制根因**——不是 λ 不敏感，而是 λ 的每一次上调都被 m 的
自适应追平了一部分。若要真正放大成本的相对权重，必须**固定 m（显式给 `big_m`）**，
否则调 λ 有一半是空转。

### 8.3 收敛曲线：平台确实推迟了

| 周期 | 平台起点（1e-2） | 平台起点（1e-1） | 总下降 | λ·path | 路径贡献上限 |
|---:|---:|---:|---:|---:|---:|
| 1 | 22 | **57** | 1,103,134 | 43,491 | 3.94% |
| 2 | 45 | **97** | 1,551,480 | 59,794 | 3.85% |
| 3 | 93 | 88 | 4,290 | 52,810 | — |

搜索在成本维度上活跃代数明显延长（22→57、45→97 代），说明 λ 确实把一部分选择压力
转移到了成本。**但路径对总改进的贡献上限仍只有约 3.9%**（1e-2 时 1.12%）。

### 8.4 polish：增益依然 100% 来自 F1，与 λ 无关

| 周期 | gain | 若全来自路径需 path_before | 实测 path | 判定 | path 不变时 ΔF1 |
|---:|---:|---:|---:|---|---:|
| 1 | 3,485,839 | 1,546,586 km | 435 km | ✘ 不可能 | +5.21 |
| 2 | 11,218,769 | 1,081,934 km | 598 km | ✘ 不可能 | +16.37 |
| 3 | 3,561,284 | 703,097 km | 528 km | ✘ 不可能 | +11.90 |

λ 放大 10 倍后，polish 的增益**依然全部来自"救回任务"（F1）**，航程贡献依旧≈0。
与 §3 的预期完全一致：**L3（早退）与 λ 正交，λ 改不动它**。

### 8.5 结论更新

| 层 | λ=1e-2 | λ=1e-1 | λ 的效果 |
|---|---|---|---|
| L1 适应度比值 | 8040:1 | 1819:1 | 改善 4.4×（被 m 联动吃掉一半） |
| L2 收敛平台 | gen 22 | gen 57 | 明显推迟 ✔ |
| L2 路径贡献上限 | 1.12% | 3.94% | 改善 3.5×，仍很低 |
| **L3 polish 优化航程** | **否** | **否** | **✘ 完全不受 λ 影响** |

**答案：问题依然存在。λ=1e-1 缓解了 L1/L2（航程 −3.2%、平台推迟），但 L3 这层
"path 从未被优化"的硬阻塞纹丝不动。** 唯一能同时治三层的做法是 §6 的第 1、2 条
（拆早退 + 航程进比较键），以及第 3 条（独立于主适应度的纯成本 polish）。

### 9.3 两个结论

1. **主周期航程持平（27.04 → 27.03）⇒ 修复没有真正优化航程。**
   根因：**访问顺序本来就是 DE 编码的一部分**——`cost_vector[K, N)` 巡游段，
   `test_tour_order_encoding` 已证明它被反映射真实消费。搜索充分（gen 100）时，
   DE 自己搜出的顺序不劣于「最近邻」贪心；强行用最近邻覆盖，等于用贪心替换
   搜索结果，净收益为零（冒烟档 gen 20 搜索不充分，最近邻才显得有用）。
2. **总航程 +4% 来自 3 个新增的「尾巴周期」**（42/4 完成 1 个 39 km、
   43/4 完成 1 个 58 km、44/4 完成 2 个 159 km、44/5 完成 1 个 79 km）。
   重排改变了 ETA ⇒ 少量任务被挤出当期 ⇒ 多跑一个周期才清空池子。

### 9.4 处置

- 已将 `reorder_range_optimize` 默认置回 **false**（生产口径不变），
  开关与配套测试保留作对照/复现（新增 `tests/test_reorder_range_optimize.py`）。
- **诊断结论不变**：早退确实是真缺陷（航程从未进入比较，§3 的反证依然成立）。
  被证伪的只是「最近邻」这个具体求解器。
- **下一步应选的方向**（按预期收益排序）：
  1. **2-opt / Or-opt 组内重排**代替最近邻——最近邻是构造式贪心，对 TSP 明显
     弱于 2-opt；且须**作用于交付解**（搜索后），避免干扰 DE 的顺序搜索
     （本次的教训：改在解码期会覆盖搜索结果）。
  2. **交付后纯成本 polish**：在 `monotone_polish` 之外加一段只以 `λ·path`
     为目标、约束「执行集不减、迟到不增」的局部搜索（记忆里的 P4）。
  3. **显式固定 `big_m`**：治 §8.2 的 m 联动，让 λ 的杠杆不再被自适应追平。
     成本极低（只改配置），建议与 1、2 正交单独测。

### 10.1 实现（`methods/muas/solvers/muas_stage.py`）

- 测试：`tests/test_cost_polish_delivered.py` 7 项（ETA 一致性 / 压航程+

### 10.6 适用域注记：polish 的价值取决于航程长度

零接受是**实例结构**决定的，不是方法无效：exp01 的配额口径
`n_sel = min(⌈max_ratio·K⌉, cap(t))` 把每机航程压在 1.6~2 个任务
（K=10、n_sel=20），2-opt 的邻域本来就只剩「换不换这两个的顺序」。
航程越长（积压域 exp06 的 arr≥25、或 max_ratio 上调），段反转/段迁移
的邻域规模按 O(n²) 增长，贪心插入的次优性才会暴露——**该 polish 是
为长航程口径准备的基础设施，默认开启、零风险（只接受严格改进），
在 exp01 上表现为恒等操作**。若后续 exp06 积压格出现接受，本章的
四道门与采纳判据即直接复用。

## 11. 归属维度 pivot：跨机改派成本 polish（2026-10-24 晚，用户裁定）

§10 钉死了「顺序维度无余量」；§10.4 同时指出 relocate 每周期接受
4~10 次——但那是在 DE 适应度（被 `m·F1` 支配）驱动下发生的，救回
超期任务的优先级远高于压航程。用户据此裁定：**把成本优化从「组内
重排」转到「跨机指派」，且继续作用于交付解（不拧适应度）**。

### 11.1 与既有 relocate 的结构差别（为什么不复用 `_polish_routes_monotone`）

| | `polish_assignment` / `_polish_routes_monotone` | 新增 `_cost_polish_relocate` |
|---|---|---|
| 作用对象 | DE 搜索期候选解 / gate 模式终态 | **交付解**（搜索后，`post_cost_polish` 内） |
| 优化目标 | 适应度 `f`（F1 主导，顺带覆盖） | **纯航程**（执行集守恒） |
| 门禁口径 | 覆盖优先（可增任务） | 执行集**不减持**（任务只换机不丢失） |
| 生产启用 | `polish_assignment` 在 DE 环内默认开 | `cost_polish_relocate_enabled`（默认 true） |

关键差别是**优化目标**：DE 环内的 relocate 为了 F1 愿意牺牲航程；
交付后的 relocate 在保持任务集不变的前提下只问「这单任务换台机器
能否更便宜」。二者互补而非重复——搜索管覆盖，交付后 polish 管成本。

### 11.2 实现（`muas_stage.py`）

- `_cost_polish_relocate(routes, ends)`：对每个 (src, 位置, 任务, dst)
  计算机械最优插入位的净变化
  `Δ = tour_cost(src\{tid}) + tour_cost(dst∪tid) − tour_cost(src) − tour_cost(dst)`；
  受体含**可用但空闲的机**（起终点按当前位置估价，终点巢由下游
  `_choose_end_nests` 重选）。四道门逐机判定：两侧航程门
  （`_range_limit`）、两侧迟到门（`_late_key` 逐分量）、执行集由构造
  保持、净航程严格降 > eps。first-improvement + 接受即重启，按 id
  升序无随机，逐位可复现。
- `post_cost_polish` 升级为**联合局部搜索**：改派（归属）↔ 组内
  2-opt/Or-opt（顺序）交替，一个完整联合轮次零接受即停（上限 3 轮
  防御二阶交互——改派改末任务、末任务改返航腿与巢容量竞争）。
- 诊断键 `blocked_range` / `blocked_late`：几何更优但被航程门/迟到门
  拦死的改派数——用于区分「无余量」与「有余量被约束堵住」。
- 采纳判据（`run_selective_muas` 内，与 coverage_first 终态后处理
  同构）：执行集 ⊇ 旧解 且 硬违约不增 且 交付航程严格下降；被拒则
  交付解原样返回。
